# Vilaow API

FastAPI + PostgreSQL. Serves the admin panel and the public site.

## Running it locally

```bash
cd backend
cp .env.example .env
uv sync
createdb vilaow
uv run alembic upgrade head
uv run python -m app.seed --owner you@example.com --password 'choose-one'
uv run uvicorn app.main:app --reload --port 8400
```

Port 8400 because that is the site's default `NEXT_PUBLIC_API_BASE`.

**It will refuse to start if `DATABASE_URL` points at a hosted database while
`ENVIRONMENT` is anything but `production`.** That is not paranoia: this repo's
`.env` shipped pointing at the Render production database, so every local run
wrote to real records and any signing link it emailed a real professional
pointed at `localhost:3000`. For a deliberate one-off against production, set
`VILAOW_ALLOW_HOSTED_DB=1` — and `PUBLIC_SITE_URL` to the real site, which the
same check insists on.

Loading the client's contact spreadsheet:

```bash
uv run python -m app.seed --contacts /path/to/Vilaow-Contacts.xlsx
```

Safe to run twice — it dedupes on the phone number, against both the database
and the file itself.

## Tests

```bash
createdb vilaow_test
uv run pytest
```

They run against a real Postgres rather than SQLite, because the schema uses
Postgres enums, `ARRAY` and `JSONB`, and the overdue-lead rule depends on
timezone-aware comparison. Tests that need the client's spreadsheet skip
themselves when it is not present.

## One-off scripts

```bash
uv run python -m scripts.migrate_photo_data_urls          # report
uv run python -m scripts.migrate_photo_data_urls --apply
```

Moves photos that were stored as base64 in `professionals.photo` into object
storage. Signing used to post a `data:` URL that was written onto that column
verbatim, and the column is selected by every list response — the worklist
returns fifty rows at a time. Idempotent; safe to run against production once
`FIREBASE_BUCKET` is set.

## Before launch

```bash
uv run python -m scripts.check_launch_ready
```

Exits non-zero while anything below is outstanding, so it can gate a deploy.

The public statistics on the homepage are computed honestly from whatever is in
the database — which means demo rows become real claims. A test listing counts
as a vetted professional; a closed introduction from a test address counts as a
purchase supported; a review written to try the form appears as a verified
consumer review. On a live commercial site the last one is an offence under the
EU Unfair Commercial Practices Directive, however well intentioned.

Four things need the client and cannot be resolved here:

| | |
|---|---|
| The legal entity name, address and contact for the privacy policy | GDPR Art. 13 requires an identifiable controller; the page renders visible placeholders until it is supplied |
| The four reviews attributed to Google | No code creates them — they came from his own sample content, and he flagged it himself in `client-reference/handover/README.md` item 5. Import them with provenance or remove them |
| What "vetted" and "five-point verification" mean | The site claims licence, insurance, identity, interview and client references are checked. None exists as a field, a gate or a workflow. Either capture the checks in the pipeline or soften the copy |
| A signing route for someone who cannot use a pointer | The signature pad cannot be operated from a keyboard, which is WCAG 2.1.1 Level A on the one binding flow. A typed-signature fallback is a decision about his own agreement |

## Deploying

### First deploy, in order

1. **Render Dashboard → New → Blueprint**, pointed at `RahulPrem-appD/valow-mono`.
   It reads `render.yaml` from the repo root and creates three things: the
   `vilaow-api` web service, the `vilaow-review-requests` cron job, and a
   Frankfurt `vilaow-db`.
2. Render **prompts for six values** — they are marked `sync: false` so they are
   never in git:

   | | |
   |---|---|
   | `CORS_ORIGINS` | `https://valow-mono.vercel.app` (the site's real origin, or the custom domain) |
   | `PUBLIC_SITE_URL` | the same origin — this is what goes in emailed signing links |
   | `SMTP_USER` / `SMTP_PASSWORD` | the Gmail account and its app password |
   | `FIREBASE_BUCKET` | `vilaow-greece.firebasestorage.app` |
   | `FIREBASE_CREDENTIALS_FILE` | the path of the service-account JSON, mounted as a Render **secret file** |

   `SECRET_KEY` is generated by Render. Do not set it by hand.
3. The container runs `alembic upgrade head` before uvicorn binds, so the new
   database migrates on first boot. Verified locally from empty and from
   production's exact current state — data preserved either way.
4. Point the Vercel project's `NEXT_PUBLIC_API_BASE` at the new API URL and
   redeploy the site. Until this is done the site renders "The directory is not
   loading right now", which is what it does today.
5. `uv run python -m app.seed --owner … --password …`, then load the contact
   sheet.

If a value is missing the service **refuses to start** and names everything that
is wrong at once, rather than coming up green and failing per request. That is
deliberate — see `validate_for_production`.

### The Oregon database

The blueprint creates a **new** Frankfurt database. The existing Oregon one is
not touched and not reused. It holds one professional, nothing published and no
imported contacts, so there is nothing to migrate across — retire it once the
new one is serving.


`render.yaml` (repo root) describes the service and its database. Both are pinned to
**Frankfurt**, and that is not a preference:

- it is intended to hold contact details for 327 real Greek businesses, which
  is personal data under GDPR for every sole trader among them
- Render cannot move a service or a database between regions after creation,
  so getting it wrong means rebuilding both

Migrations run at container start, before uvicorn binds. Render has no separate
release phase, so this is the only reliable moment to apply them.

**Checked 2026-08-17 against the live database.** It is still in Oregon, and it
is on the *initial* migration only (`2bc351640e80`) — the second one, which adds
profession fields, introductions, assets and `professionals.custom`, has never
run there. It holds one professional, nothing published, and no imported
contacts, and `vilaow-api.onrender.com` answers 404, so the live site renders
"The directory is not loading right now". Nothing built since 10 August is
deployed.

Two consequences worth naming. The region move is cheap *now* — an almost empty
database — and expensive once the 327 contacts are imported. And a container
that boots runs `alembic upgrade head` first, so the schema being frozen at the
first revision means no current container has ever booted successfully.

### Environment

| Variable | Required | Notes |
|---|---|---|
| `DATABASE_URL` | yes | Render supplies `postgres://`; the app rewrites it to `postgresql+psycopg://` |
| `SECRET_KEY` | yes | Signs session cookies. **The app refuses to start in production if this is left at the default** — otherwise cookies would be signed with a value published in this repo |
| `ENVIRONMENT` | yes | `production` enables secure cookies and the check above |
| `CORS_ORIGINS` | yes | Comma separated. The site's origin, so the admin can hold a session cookie |

### After the first deploy

1. Create the owner account:
   `uv run python -m app.seed --owner asaf@vilaow.com --password '...'`
2. Load the contact sheet.
3. Set `CORS_ORIGINS` to the real site origin and redeploy.

## Notes for whoever picks this up

**Sessions carry an id and nothing else.** Role is read from the database on
every request. A cookie that carried `role=owner` would be a cookie its holder
could forge.

**Passwords go through SHA-256 before bcrypt.** bcrypt reads at most 72 bytes
and silently ignores the rest, so a long passphrase would otherwise be only as
strong as its first 72 characters. `passlib` is not used: it is unmaintained
since 2020 and rejects a fifteen-character password against bcrypt 5.

**The importer walks the spreadsheet, it does not assume a header row.** The
client's sheet is grouped for reading — region bands, city bands, and the
`Category` header repeated once per city — and it has no city column at all.
The city is the band you are standing in.

**Reviews have no edit path, deliberately.** His listing agreement commits in
writing that reviews "cannot be bought, edited or removed on request".

**Ratings are shown with attribution.** `source` records where a rating came
from; publishing another platform's numbers without saying so is not something
to do by accident.
